# 车险前端金额精度检查与处理

## 原因与范围

JavaScript Number采用二进制浮点表示，`235.58 + 23`得到`258.58000000000004`。直接插值显示会把内部尾差暴露给用户。仅调用`toFixed(2)`虽能隐藏多数尾差，但`(1.005).toFixed(2)`可能得到`1.00`，不能作为精确金额计算方案。

本次扫描三个应用的全部源码：`frontend/src` 67个、`systemportal/src` 54个、`monitor-frontend/src` 38个JS/Vue文件，共159个，针对金额、比例、算术运算和模板显示逐项核查；public目录只有静态HTML/CSS/图片。确认并处理以下车险页面：

| 位置 | 原问题 | 处理 |
| --- | --- | --- |
| 工单详情保费、上游费用、下游费用合计 | 原始值直接相加，产生浮点尾差；字符串金额可能被拼接 | 十进制精确求和，最终显示两位小数 |
| 报价、核保表单合计保费 | 浮点求和再toFixed；空字符串或null经Number转换被当成零 | 精确求和；全空显示空白，明确零显示0.00 |
| 报价、核保上下游各险种政策预览 | 浮点乘除后toFixed，在舍入临界点可能少一分 | 整数分数计算，仅最终HALF_UP到分 |
| 详情单项保费、政策费用、发票金额 | 接口金额直接显示，无统一小数位保护 | 只读金额统一两位小数；发票沿用原未填写判定 |
| 总览、接单、派单共用列表费用展示 | 接口金额原样透传，可暴露已有浮点尾差 | 共用格式化；已报价缺失费用显示0.00，未报价继续空白 |

续保入口复用列表展示函数，但当前没有上下游费用列。本次扩大检查后同步修复了门户和监控：

| 应用/入口 | 发现的问题 | 处理 |
| --- | --- | --- |
| 门户充值列表、订阅订单、钱包流水、套餐页 | 直接输出接口金额，没有小数位保护 | 全部接入统一两位小数展示 |
| 门户订单/充值详情、企业信息、官网价格及两端仪表盘 | 先Number转换再toFixed或本地化，丢失字符串精度或临界分位 | 直接处理原始十进制字符串；保留千分位及官网整数价格风格 |
| 门户订阅试算页余额缺口 | 浮点减法产生尾差，路由传递缺口可能携带尾差 | 精确相减并输出两位字符串；是否余额不足按原始十进制比较 |
| 监控企业列表/详情、财务记录和套餐管理 | Number转换丢精度，部分本地化只设置最少小数位 | 统一精确金额展示，同时限制两位小数 |
| 监控充值趋势图 | 默认tooltip/坐标轴没有金额格式规则 | 金额图显式启用money模式；计数图维持数量语义 |
| 两端环比、车险政策比例 | 直接显示接口比例，缺少尾差保护 | 按已有政策比例DECIMAL(8,2)精度最多两位，省略尾零，不二次乘100 |
| 门户mock订单试算/余额、监控mock调账 | mock也采用浮点乘除、加减 | 复用精确求和、乘除、周期折算和余额缺口工具 |

保留的普通数值运算包括：时间戳/天数转换、页数计算、整数次数汇总、图表内部绘图数值转换和mock环比的一位近似值。它们不是金额结算路径；剩余天数/周期及mock环比已有明确的小数位收敛，未发现直接暴露长尾的相同问题。车辆重量/排量等字段为用户输入或接口直出，本次没有擅自引入未经业务定义的精度限制。

## 统一实现

`shared/money.js`集中提供`formatMoney`、`sumMoney`、`calculatePolicyAmount`、`moneyShortfall`、`compareMoney`、`multiplyMoney`及`formatPercentage`，三个应用的`src/utils/money.js`仅重导出同一实现。以BigInt整数系数和十进制倍率处理十进制输入，在最终展示时按HALF_UP舍入到分，支持数字、金额字符串和科学计数法，不添加依赖。BigInt要求支持该能力的现代浏览器，不提供旧浏览器数值降级，以免悄悄恢复浮点运算。

- 缺失、空白、非法值不作为有效金额，缺失与零严格区分；负数保留符号，舍入后负零显示0.00。
- 合计沿用后端BigDecimal先相加再展示的顺序，不提前舍入分项。
- 政策预览沿用后端`Workorder.percentageCompute`：类型1为`保费 × 比例 / 106`，其他类型为`保费 × 比例 / 100`。仅最终展示到分，后端仍是实际结算依据。
- 后端原始金额可能具有分以下精度；本次不改变后端计算、接口字段类型或数据库；充值提交仍为两位十进制金额字符串。只读格式化结果不得回写作为新的业务原值。
- 输入若已经是丢失有效数字的Number，前端无法恢复。高精度金额跨接口时宜使用十进制字符串，后端继续使用BigDecimal和数据库DECIMAL。若要调整传输类型，应另行同步接口契约与各消费方。
