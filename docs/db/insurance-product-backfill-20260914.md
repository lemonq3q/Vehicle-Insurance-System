# 企业险种目录补数与清理范围核查

## 当前数据与补数方案

本次核对的连接目标为本机 MySQL `insurance_saas`。`biz_insurance_product` 是创建工单时 `/insurance/all` 接口读取的险种目录；`biz_workorder_insurance` 是工单创建后保存所选险种的明细表，不应预先填入目录数据。当前 `biz_workorder` 为 0 行，因此向工单险种明细表复制旧工单数据会产生孤儿关联。

执行前有效险种数：企业 1（小e保存量业务）0 条，企业 2（李梅测试企业）0 条，企业 3（测试）23 条。企业 3 的 23 条险种名称互不重复。`backend/db/migration/V20260914_01_backfill_missing_enterprise_insurance_products.sql` 以企业 3 的有效险种为模板，仅为当前无有效险种的企业复制险种名称、类型、可选项、默认值和备注，并重新生成每个企业的主键及创建/更新时间。执行后实际新增 46 行；再次执行应新增 0 行。企业 3 原记录未修改。

2026-09-14 在本机 `insurance_saas` 执行了上述单条 `INSERT ... SELECT`，结果为 `affectedRows=46`、无重复及警告。执行后企业 1、2、3 各有 23 条有效险种；逐字段比对，企业 1、2 的 23 条与模板的名称、类型、选项、默认值及备注一致；`biz_workorder_insurance` 仍为 0 行。初版脚本含多条语句，执行器在第一条写入前拒绝解析；确认数据库未变化后，改用单条原子插入成功，并将本脚本整理为同一条可重放语句。

企业创建接口已在 `EnterpriseServiceImpl.create` 的事务内调用 `insertDefaultInsuranceProducts`，使用随 SaaS 服务发布的标准险种资源初始化新企业。因此补数主要修复创建逻辑上线前已存在的企业，不需要再增加一次创建时初始化逻辑。

## 企业专属或平台共用

当前模型选择了企业专属险种：`biz_insurance_product.enterprise_id` 由车险 MyBatis 租户插件约束，工单险种明细通过 `insurance_id` 关联各企业自己的险种主键，企业创建时直接复制标准目录。这种方式可以允许未来按企业调整选项或默认值。缺点是每家企业都维护一份相同目录，老企业需要补数。当前表只有主键索引，没有 `enterprise_id` 索引；企业数量增加后，按企业筛选目录会退化为全表扫描。

如果产品规则确定所有企业始终使用相同且不可编辑的险种，可考虑平台共用目录。那需要另做版本化改造：将公共险种从租户插件的强制 `enterprise_id` 过滤中排除，调整 `/insurance/all` 的查询与工单写入校验，明确已存在工单的 `insurance_id` 如何迁移，并将公共目录移出企业资料清理白名单。不能只删除 `enterprise_id` 列或索引，否则现有查询与清理流程会失效。

在没有确认“险种永远不可按企业定制”之前，建议保留现有企业专属模式，先补齐历史企业，再单独处理清理后重新订阅的初始化问题，并评估增加 `(enterprise_id, deleted)` 索引。此次补数脚本不改表结构或应用代码。

## 企业资料清理核查

实际触发条件不是“连续欠费超过 3 个月”。SaaS 每日 04:00 的维护任务使用订阅最近的 `end_at <= 当前时间 - retentionDays` 筛选企业，默认 `retentionDays=90`；`plan_id` 和 `end_at` 必须非空。余额欠费会暂停车险登录，但不会单独启动这项 90 天资料清理。

2026-09-14 调整后，车险域 `EnterpriseBusinessDataPurgeService` 的固定归档清单保留 `biz_workorder_insurance`，不再包含 `biz_insurance_product`。当企业符合清理条件时，已选险种明细随所属工单一起归档并从在线表移除；企业险种目录保持在线，重新开通套餐后可继续使用。若 OSS 删除或事务失败，数据库在线数据不会完成本轮清理。

险种目录现在不再由企业资料清理服务移除。工单险种明细仍属于工单生命周期，不能单独保留在在线表中，否则会引用已经归档的工单。此前已经完成清理、在线目录确实为空的企业仍需另行补数；本次代码调整不会自动从归档表恢复历史记录。
