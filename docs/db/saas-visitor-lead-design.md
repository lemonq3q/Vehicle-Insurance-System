# SaaS 官网游客信息数据库设计

## 1. 设计范围

本设计用于承接 SaaS 门户官网“联系我们”表单，并供监控系统按游客编号查询。当前仅设计游客信息入库能力，不包含客服微信二维码生成、二维码图片存储、线索分配、跟进状态或跟进记录。

数据库基线为 MySQL 8.0，沿用项目现有的 `utf8mb4_0900_ai_ci`、自增 `BIGINT` 主键、软删除字段和创建/更新时间字段规范。

## 2. 表设计

本功能仅使用 `saas_visitor_lead` 一张表。一条游客提交对应一条线索记录，合作诉求通过主表的 `intent_codes` JSON 数组保存，不单独建立合作诉求明细表。

## 3. saas_visitor_lead 游客线索主表

| 字段 | 类型 | 是否必填 | 说明 |
| --- | --- | --- | --- |
| `id` | `BIGINT` | 是 | 自增主键，仅供数据库内部关联 |
| `lead_no` | `VARCHAR(32)` | 是 | 对外游客编号，全局唯一；建议格式 `VLyyyyMMdd` + 10 位随机大写字母数字，例如 `VL20260828A7K3M9Q2X5` |
| `name` | `VARCHAR(100)` | 是 | 游客姓名，提交前去除首尾空格 |
| `contact` | `VARCHAR(100)` | 是 | 用户填写的联系方式，可承载手机号、微信号或邮箱；当前表单未区分联系方式类型，因此不拆列 |
| `role_code` | `VARCHAR(32)` | 否 | 角色编码：`OPC_AGENT`、`CAR_DEALER`、`INSURANCE_AGENCY`、`OTHER` |
| `expected_monthly_orders` | `INT UNSIGNED` | 否 | 预计月单量，填写时必须为非负整数 |
| `intent_codes` | `JSON` | 否 | 合作诉求编码数组，例如 `["TRIAL","DEMO"]`；允许值为 `TRIAL`、`DEMO`、`CUSTOM_COOPERATION` |
| `remark` | `VARCHAR(1000)` | 否 | 游客备注 |
| `created_at` | `DATETIME` | 是 | 提交时间，数据库默认当前时间 |
| `updated_at` | `DATETIME` | 是 | 最后更新时间，数据库自动维护 |
| `deleted` | `TINYINT` | 是 | 软删除标记：`0` 正常、`1` 删除 |

索引与约束：

- `uk_saas_visitor_lead_no (lead_no)`：保证编号全局唯一，也是监控系统按编号精确查询的主要索引。
- `idx_saas_visitor_lead_created (deleted, created_at, id)`：支持监控页面默认按最新提交时间倒序展示及分页。
- `chk_saas_visitor_lead_role`：限制角色编码只能取当前四种值。
- `chk_saas_visitor_lead_monthly_orders`：限制预计月单量不小于 0。
- `chk_saas_visitor_lead_intent_codes`：合作诉求非空时，限制为包含一至三个元素的 JSON 数组。允许值及元素去重仍由后端参数校验严格保证。

## 4. 编号生成规则

编号由后端在写入事务开始前生成，数据库只负责唯一性兜底，不使用自增主键拼接，避免暴露线索数量。

- 格式：`VL` + `yyyyMMdd` + 10 位随机大写字母数字。
- 示例：`VL20260828A7K3M9Q2X5`。
- 字符集建议排除容易混淆的 `0/O`、`1/I/L`。
- 写入发生极低概率唯一键冲突时，后端重新生成编号并重试，建议最多重试 3 次。
- 后续二维码内容携带 `lead_no`，而不是数据库 `id`。具体二维码 URL、场景值和有效期在二维码功能设计阶段确定。

## 5. 写入与业务校验

一次提交应在同一事务中完成：

1. 校验姓名和联系方式非空并限制长度。
2. 角色填写时校验编码属于允许集合。
3. 预计月单量填写时校验为非负整数。
4. 合作诉求有选择时校验所有编码属于允许集合并去重，然后序列化为 JSON 数组；未选择时存储 `NULL`。
5. 生成 `lead_no`，将全部表单数据一次写入主表。
6. 写入失败时整体回滚，不产生不完整数据。

## 6. 查询约定

监控系统查询条件仅提供 `lead_no`：

- 输入编号时使用精确匹配 `lead_no = ?`，不使用模糊查询，以确保命中唯一索引。
- 未输入编号时按 `created_at DESC, id DESC` 分页展示全部未删除记录。
- 合作诉求直接读取 `intent_codes` 并反序列化为字符串数组，不需要关联查询。

## 7. 隐私与边界说明

- `name`、`contact` 属于个人信息；监控系统接口和页面需要纳入登录鉴权，日志中不得直接打印完整联系方式。
- 当前没有明确提出线索处理流程，因此不预设处理状态、负责人、跟进备注等字段；后续确认客服跟进流程后再单独建模。
- 当前“其他”只作为角色选项，不额外保存“其他角色说明”。如果产品要求用户填写具体身份，应再增加可空字段 `role_other_text VARCHAR(100)`，并仅在 `role_code = 'OTHER'` 时允许填写。
