# 监控平台销售推广目标表设计

> 状态：表结构、前后端与 API 契约已实现；数据库迁移已于 2026-08-27 执行并核验  
> 目标数据库：`insurance_saas`（MySQL 8.0）  
> 迁移脚本：`backend/db/migration/V20260827_02_create_monitor_promotion_target.sql`

## 1. 设计范围

本阶段只设计“销售推广 / 信息录入”所需的推广目标主表。每行代表一个可被推广触达的目标，支持页面单条新增、编辑、软删除、分页查询和 Excel 批量导入。

推广任务、逐条发送记录、失败重试、退订记录和渠道供应商回执不属于本表职责。待真实短信、电话或邮件 API 接入时，应另建推广任务表与发送明细表，不能把不断增长的发送历史堆入目标主表。

## 2. 核心决策

- 表名使用 `monitor_promotion_target`，归属监控平台独立的 `monitor_*` 表族，不挂靠 `tenant_enterprise`。
- `name`、`phone`、`email` 是当前确定的常用字段；电话和邮箱允许为空，以适配只具备单一渠道联系方式的数据。
- `extra_fields` 使用 JSON 保存未来暂未固定的推广属性。字段一旦成为列表筛选、排序、唯一性判断或高频统计条件，应通过后续迁移提升为独立列并建立索引，不能长期依赖 JSON 全表扫描。
- 不对电话或邮箱建立唯一约束。现实中同一联系方式可能对应家庭、企业公共电话或多人邮箱；导入阶段可提示重复，但是否合并由业务规则决定。
- 删除采用 `deleted=1` 软删除，保留导入来源和操作人，便于审计与误删恢复。
- 当前每次推广最多选择 6000 条是服务层业务配置，不写成数据库约束。无条件全选时，后端应先统计有效目标数并明确提示截断，再固定按 `id ASC` 选取前 6000 条，保证结果稳定。

## 3. 字段定义

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | `BIGINT` | 是 | 自增 | 推广目标主键，也是批量选择的稳定游标 |
| `name` | `VARCHAR(100)` | 是 | - | 推广目标名称，可为个人姓名或业务联系人名称 |
| `phone` | `VARCHAR(32)` | 否 | `NULL` | 电话号码；长度兼容国家区号、分机号等格式 |
| `email` | `VARCHAR(254)` | 否 | `NULL` | 邮箱地址，长度按通用邮件地址上限预留 |
| `extra_fields` | `JSON` | 否 | `NULL` | 扩展推广字段，键使用稳定英文编码，例如 `companyName`、`position` |
| `source_type` | `VARCHAR(16)` | 是 | `MANUAL` | 数据来源：`MANUAL`、`EXCEL_IMPORT`；后续增加来源时扩展枚举 |
| `import_batch_no` | `VARCHAR(64)` | 否 | `NULL` | Excel 导入批次号；手工录入为空，可用于定位和回溯整批数据 |
| `status` | `TINYINT` | 是 | `1` | `1` 可推广，`0` 停用；停用数据不进入默认推广候选集 |
| `remark` | `VARCHAR(500)` | 否 | `NULL` | 运营备注，不作为推广消息内容 |
| `created_by` | `BIGINT` | 否 | `NULL` | 创建人 `monitor_user.id`；系统导入可为空 |
| `updated_by` | `BIGINT` | 否 | `NULL` | 最后修改人 `monitor_user.id` |
| `deleted` | `TINYINT` | 是 | `0` | `0` 正常，`1` 软删除 |
| `created_at` | `DATETIME` | 是 | 当前时间 | 创建时间 |
| `updated_at` | `DATETIME` | 是 | 当前时间并自动更新 | 最后更新时间 |

业务校验要求：

- 当前版本新增或导入时，`phone`、`email` 至少填写一项；此规则放在应用层，避免未来增加新渠道字段后受到数据库 CHECK 约束阻碍。
- 写库前对名称去除首尾空格；空字符串电话或邮箱统一转成 `NULL`。
- 电话保留用户导入的可拨号字符，后端另做格式校验；邮箱比较和精确查询时统一使用小写值。
- `extra_fields` 只能存放模板或接口契约中声明过的键，禁止前端任意提交未知键。
- 删除、停用数据不得进入推广选择范围。

## 4. 索引与主要查询

| 索引 | 用途 |
| --- | --- |
| 主键 `PRIMARY KEY (id)` | 单条 CRUD、稳定批量游标 |
| `idx_promotion_target_list (deleted, status, id)` | 默认列表与无条件全选；支持 `WHERE deleted=0 AND status=1 AND id>? ORDER BY id LIMIT ?` |
| `idx_promotion_target_name (deleted, name, id)` | 名称前缀搜索及稳定翻页 |
| `idx_promotion_target_phone (deleted, phone, id)` | 电话精确或前缀搜索、导入重复检查 |
| `idx_promotion_target_email (deleted, email, id)` | 邮箱精确或前缀搜索、导入重复检查 |
| `idx_promotion_target_batch (import_batch_no, id)` | 导入结果回溯与批次错误定位 |
| `idx_promotion_target_created (deleted, created_at, id)` | 按录入时间筛选和倒序列表 |

包含匹配（`LIKE '%关键字%'`）无法有效利用普通 B-Tree 索引。首版可在数据量可控时使用；若数据规模明显增长，应引入专用搜索方案，不能通过堆叠组合索引解决。

## 5. 与推广页面的关系

推广页面的“根据搜索条件批量选择”应复用信息录入列表的同一套查询条件。请求中应区分两种选择模式：显式 ID 集合与按查询条件全选。后端最终生成收件人集合时统一追加 `deleted=0 AND status=1`，再按所选渠道过滤对应联系方式非空的数据。

无条件全选的推荐流程：

1. 统计当前渠道下具备有效联系方式的目标总数。
2. 如果超过当前配置 `6000`，返回总数、上限及“仅发送前 6000 条”的明确提示。
3. 用户确认推广后，以 `id ASC` 稳定选取最多 6000 条；不能先把全量 ID 加载进 JVM 再截断。
4. 推广任务创建后应保存收件人快照。该能力将在后续推广任务与发送明细表设计中完成。

## 6. 数据安全与审计

- 电话和邮箱属于个人信息。列表默认脱敏展示，只有具备销售推广权限的监控平台账号可查询原值或发起推广。
- 导出、批量导入、批量删除和发起推广应写入现有 `monitor_system_log`；日志摘要和错误信息不得记录完整电话、邮箱或推广正文。
- 当前项目同类联系方式使用明文列，为保持搜索与现有架构一致，本表暂不引入独立加密方案。真实渠道接入前应再次评估列加密、密钥管理和数据保留期限。
- 后续必须补充退订/拒绝营销机制；被退订的联系方式在所有渠道发送前都要统一拦截。

## 7. 暂不设计为字段的内容

- 6000 条推广上限：属于可配置服务规则。
- 自定义推广文案：属于一次推广任务，不属于目标资料。
- 渠道发送状态、供应商消息 ID、失败原因：属于发送明细。
- 累计推广次数、最近推广时间：可由发送明细汇总；若后续列表性能需要，再增加派生快照字段。
