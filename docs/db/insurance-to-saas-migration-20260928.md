# insurance 存量数据合并迁移

## 交付与库名

脚本：`backend/db/migration/migrate_insurance_to_saas.py`。
测试：`backend/db/migration/test_migrate_insurance_to_saas.py`。

2026-09-28 通过本地 MySQL MCP 核实，实际库名为 `insurance` 和 `insurance_saas`，
不存在 `saas_insurance`。脚本要求显式传入 `--target`，不会自动猜测或创建数据库。
如果其他环境实际命名为 `saas_insurance`，可直接更改该参数，前提是结构一致。

这是向已有 SaaS 数据追加一个独立企业的脚本，不要求清空目标库，不沿用旧脚本中的
固定企业 ID=1。旧版 `V20260714_01_migrate_insurance_to_saas.sql` 保持原样。

仅使用 Python 3.9+ 标准库及 MySQL 客户端；服务器要求 MySQL 8.0.16+，本地验证版本
为 8.0.43。无需新增项目运行时依赖。没有前端、mock 或 HTTP API 变更。

## 三阶段使用

以下命令在仓库根目录执行。`--password-prompt` 交互输入密码，密码不会写进命令行、
计划或对照表；也可用已经配置的 `--login-path` 或外部提供的 `MYSQL_PWD`。
连接账号需要 SELECT；执行还需要 INSERT、LOCK TABLES、CREATE TEMPORARY TABLES 权限。

```powershell
# 1. 只读预览；目录必须为空或不存在，保留已审阅的历史计划。
python backend/db/migration/migrate_insurance_to_saas.py preview `
  --source insurance --target insurance_saas `
  --enterprise-code LEGACY_INSURANCE_20260928 `
  --enterprise-name "小马e保存量业务" `
  --plan-dir outputs/database/insurance-migration-reviewed-20260928 `
  --password-prompt

# 2. 只读验证计划是否仍有效，并让 MySQL 解析全部业务 INSERT。
python backend/db/migration/migrate_insurance_to_saas.py validate `
  --source insurance --target insurance_saas `
  --plan-dir outputs/database/insurance-migration-reviewed-20260928 `
  --password-prompt

# 3. 仅在审阅确认、完成两个库备份并停止应用写入后执行。
python backend/db/migration/migrate_insurance_to_saas.py apply `
  --source insurance --target insurance_saas `
  --plan-dir outputs/database/insurance-migration-reviewed-20260928 `
  --confirm-code LEGACY_INSURANCE_20260928 `
  --password-prompt
```

实际写入需遵守项目 `AGENTS.md`：
“数据库写操作、结构变更、数据清洗和高风险 SQL 必须先让用户审阅确认。”
本次只生成并验证计划，没有执行第三步，也没有创建永久表或修改数据库结构。
不要直接用带 `--force` 的客户端执行 SQL，否则遇错继续执行会破坏整批回滚保证。

计划目录包含：

| 文件 | 内容 |
| --- | --- |
| `migration.sql` | 完整、可审阅的插入 SQL、表锁、执行前条件、执行后数量断言及提交 |
| `manifest.json` | 企业 ID、源/目标数量、全部 ID 映射、账号变更、旧角色关系和异常规则 |
| `source-snapshot.json` | 源库全部表和全部字段的精确数据快照，保留无法一一表达的历史字段 |
| `validated.json` | 只读验证结果和 SQL 哈希 |
| `committed.json` | 只有实际提交成功后才生成的本地回执 |
| `.gitignore` | 阻止计划中的业务数据和密码哈希进入 Git |

源快照与 SQL 包含个人资料和密码哈希，应按数据库备份管理。源库保持不变；源快照
不能代替目标库的执行前完整备份。附件路径和元数据迁入，外部存储的文件内容仍依赖
原 OSS/文件存储可访问，不会下载或复制二进制文件。

## ID 冲突与关联

每类实体从目标正式表和对应归档表的最高 ID 之上重新分配主键，正式与归档共用
该实体的新 ID 序列。即使旧 ID 当前没有冲突也重新分配，不靠固定偏移量或目标同号
记录猜测关系。所有外键通过 `manifest.json.id_maps` 中的旧 ID → 新 ID 映射转换。

转换范围包括人员、成员、商户、商户区域、商户人员、险种、工单、车辆资料、文件、
工单险种和文件明细。工单的创建人、处理人、更新人分别映射为新用户，来源商户人员
单独映射为新的 `biz_merchant_staff.id`；支付记录绑定新的收款人员 ID。

归档明细可以关联正式父记录，例如 `workorder_file_archive` 关联正式工单和归档
文件；查找父实体时合并正式与归档映射。源库存在非空外键却找不到父实体时整批中止，
不置空、不借用目标库同 ID 的数据。如果源正式表与归档表出现相同实体 ID，也中止
要求先确认记录版本，避免猜测哪一条才是父实体。

商户和工单编号在新企业内保留；源库空编号或重复编号追加 `_legacy_<旧ID>` 后缀，
如果候选仍重复再加序号。业务关联依据 ID 映射，不依赖改名后的编号。

## 账号冲突

项目登录条件是 `username = 登录值 OR phone = 登录值`，不能只检查 username。
脚本同时对目标正式用户、归档用户和本次迁入用户的 username/phone 查重，使用目标
MySQL 的真实排序规则计算权重，包括大小写和重音比较。账号/手机号排序规则不一致
时中止，避免与应用登录查询产生不同解释。

- 无冲突保留原账号；11 位大陆手机号账号同时作为 phone。
- 冲突时创建独立新用户，账号追加 `_e<新企业ID>_u<旧用户ID>`，再次冲突追加序号。
- 冲突手机号置 NULL，原手机号及旧账号完整保留在对照表和源快照中。不会修改旧目标
  用户，也不会把两个同手机号的人合并，避免登录混淆或短信重置覆盖另一人的密码。
- 非手机号账号的 phone 为 NULL。商户人员的业务联系电话仍保留真实原手机号，
  与登录账号命名空间分开。
- 原 BCrypt 密码哈希不重置，不重新加密。更名账号使用新账号加原密码登录；phone
  被置空的账号在重新绑定独立手机号前不能通过原手机号找回密码。
- 删除状态、启停状态保留；未审批管理/出单人员保留成员状态 2，不自动审批。

执行前再次按数据库真实比较规则检查已有账号，提交前检查本次账号之间无登录歧义。
`manifest.json.accounts` 明确记录旧/新用户 ID、账号、phone 是否冲突及商户映射。

## 人员、企业与旧配置

全部旧用户迁入 `tenant_user` 或 `tenant_user_archive`，保留身份和审计引用。
原 admin/出单员建立成员关系，分别为 ADMIN/ISSUER；一个人有多个企业角色时折叠
为 ADMIN 优先的单成员记录。企业拥有者从未删除且启用的管理员中自动选择，优先
已审批者、再按旧 ID 排序；也可以预览时用 `--owner-old-id` 指定启用的旧管理员或
出单员。指定者不能是删除或禁用账号，旧审批状态仍保留。

下游商户绑定人员同时拆为 `biz_merchant_staff` 和人员角色。一个商户有多个有效
联系人时，旧 ID 最小者为 CONTACT，其余转为 CLERK；全部收款人保留 PAYEE，只选
一个默认收款人。完全重复的角色关系折叠，不丢弃人员，原关系历史留在源快照与
`manifest.json.relations`。上游继续使用商户 contact/phone 字段，旧用户与上游
商户的绑定对照保留在 accounts 中，不赋予不适用的下游人员角色。

旧 `role`/`menu`/`role_menu` 是旧权限配置，不能原样覆盖 SaaS 公共角色。脚本按
角色和权限码映射现有配置，验证旧权限已存在且管理/出单角色已有相应授权；不修改
既有企业的公共权限。旧人员角色关系映射为成员/人员角色，重复或过期历史保留在快照。
旧角色名称未知、目标权限缺失或未授权时中止，不自动扩大平台权限。

商户分类沿用原迁移规则：机构/保司 → INSURANCE_ORG，汽修厂 → AUTO_REPAIR，
代理人 → AGENT，车商店铺 → DEALER_STORE。未知/空类型按旧脚本兼容规则采用
DEALER_STORE 并逐项告警。本地有两条未删除商户（旧 ID 7981、13807）类型为空，
这是需在执行前审阅的历史数据语义，若实际类型不同，应先修正方案或源数据后重新预览。

新企业钱包为 0，订阅未开通，数据保留自动清理关闭；不伪造付费订单或历史充值。
直接迁入旧险种目录，不再额外插入默认险种造成重复。旧宽工单拆为工单、报价、
上下游佣金、支付、核保及物流；金额不经过浮点重算，秒时间戳按 +08:00 转 datetime，
保险起期等原 bigint 字段保留。旧 `pay_id_num` 写入 `payee_id_num`，不误当手机号。
收款人员只有商户、姓名及证件唯一匹配时才绑定，历史收款快照始终保留。

## 原子性、并发与重跑

预览用单连接只读一致性快照；所有涉及的表必须为 InnoDB。插入触发器仅允许项目
现有的 BEFORE INSERT 空时间补全逻辑，其他插入触发器要求先审阅，计划中保存并
核对触发器定义。空历史时间可能被现有触发器补成执行时间，原 NULL 留在源快照。

执行设置 `autocommit=0`，锁定源表 READ、目标写入表 WRITE 和相关配置 READ。
表锁之后不执行 `START TRANSACTION`，避免它释放表锁。锁内逐项比较源库完整行
SHA256 前 64 位异或校验值及行数，以及目标主键/行数、身份和配置指纹；发生变化
则中止并重新预览，不基于旧计划继续写。表锁会阻塞应用请求，执行前应停止业务写入。

每批使用普通 INSERT，保留目标唯一约束，不使用 REPLACE、INSERT IGNORE、关闭
外键或跳过错误。插入后核对各表数量，最后一次 COMMIT。任一错误让客户端停止并
断开，提交前的 InnoDB 写入全部回滚。临时校验表不改变永久结构。

企业编码查正式与归档，已存在则拒绝新预览；apply 检查企业编码确认参数、计划哈希
和本地提交回执。即使回执丢失，旧计划因数据库指纹/行数变化仍会被拒绝。发生提交
后连接中断时，先检查目标企业和各表，不直接重跑。
