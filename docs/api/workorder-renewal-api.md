# 工单续保跟进接口

## PUT `/workorder/renew/{id}/follow-up`

车险工单续保列表的“跟进”操作。需登录并有该工单的处理权限；`id` 为工单 ID。请求头沿用现有鉴权令牌，`Content-Type: application/json`。

| body 字段 | 类型 | 必填 | 说明 | 示例 |
| --- | --- | --- | --- | --- |
| `commercialStatus` | integer | 按商业险提醒情况 | `0` 未处理、`1` 已续保、`2` 已流失；不处理该险种时省略 | `1` |
| `compulsoryStatus` | integer | 按交强险提醒情况 | `0` 未处理、`1` 已续保、`2` 已流失；不处理该险种时省略 | `2` |
| `followUpRes` | string | 否 | 跟进备注，最多 1000 字 | `商业续保，交强流失` |

至少提交一种险种状态。两个状态同时提交时在同一次数据库更新中保存；页面根据当前周期序号是否大于零展示险种，已处理的本期险种仍展示并回填原结果，未进入提醒周期的险种不展示。服务端按保单起期、中国业务日期和当前续保周期配置决定轮次，客户端不能指定轮次。
将已处理状态改为 `0` 后，该险种重新计入本轮待处理提醒和提醒数量。

旧客户端仍可提交 `scope`（`COMMERCIAL`、`COMPULSORY`、`ALL`）与 `status`（`1`、`2`）；这两个字段不得与新状态字段混用。
当前前端只提交发生变化的险种；仅一个险种改为 `1` 或 `2` 时沿用 `scope/status` 兼容格式。改回 `0` 或同时变更两种险的不同结果使用独立状态字段，需要部署支持该契约的后端版本。

请求示例：

```json
{"commercialStatus":1,"compulsoryStatus":2,"followUpRes":"商业续保，交强流失"}
```

成功响应沿用统一外壳：`{"code":200,"msg":"已保存续保跟进","data":null}`。常见失败：`400` 参数、状态或当前提醒周期不合法；`404` 工单不存在或无权限；`400` 工单提醒已关闭或状态已变化，需刷新后重试。

联调用响应 mock 位于 `frontend/src/mock/workorderRenewalMock.js`，其中双险种请求示例与本契约一致。
